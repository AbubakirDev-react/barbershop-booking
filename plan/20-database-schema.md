# 20. База данных: Схема и безопасность

---

## 1. Основные сущности

| Сущность | Описание |
|----------|----------|
| `profiles` | Профили пользователей (клиенты, мастера, владельцы) |
| `roles` | Роли и разрешения |
| `masters` | Мастера (профиль + расписание + услуги) |
| `services` | Услуги (цена, длительность, категория, фото) |
| `categories` | Категории услуг |
| `master_services` | Связь мастер — услуга |
| `schedules` | Рабочие часы мастеров |
| `breaks` | Перерывы и исключения |
| `appointments` | Записи |
| `appointment_items` | Услуги внутри записи (снимок цены и длительности) |
| `status_history` | История изменения статусов |
| `notifications` | Внутренние уведомления |
| `notification_tasks` | Задачи отправки внешних сообщений |
| `reviews` | Отзывы |
| `shop_settings` | Настройки барбершопа |
| `audit_log` | Журнал административных действий |

---

## 2. Требования к таблицам

Для каждой сущности определи:

- [ ] Первичный ключ
- [ ] Внешние ключи
- [ ] Типы данных
- [ ] Обязательные поля
- [ ] Ограничения (check, unique, not null)
- [ ] Индексы для фильтров и связей
- [ ] Политику удаления / архивирования
- [ ] Права чтения / изменения (RLS)

---

## 3. История цены

В `appointment_items` сохраняй снимок:

- `service_name`
- `price` (на момент бронирования)
- `duration_minutes`

> Изменение каталога **не должно** менять историческую стоимость записи.

---

## 4. Безопасность Supabase (RLS)

- ✅ Включи RLS на таблицах с приватными данными
- ✅ Напиши политики для каждой роли
- ✅ Используй серверные проверки полномочий
- ✅ Защити операции изменения статусов и создания записей
- ❌ Не доверяй пользовательским значениям цены, длительности, роли
- ❌ Не используй `service_role_key` в клиентском коде
- ❌ Не открывай доступ к таблицам только потому, что UI скрывает страницы
- ✅ Добавь индексы для частых фильтров и JOIN
- ✅ Миграции должны быть повторно применимы

---

## 5. Migration safety

- ❌ Не меняй production-схему разрушительно без бэкапа и явного разрешения
